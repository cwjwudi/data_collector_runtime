## 3. 详细修改清单

### C01｜P0 前置：确定受监管记录和系统边界

**依据：** §11.1–11.3、§11.10(a)(c)。现有项目说明把 Runtime 采集数据、报表直接统称为 Part 11 记录，缺少逐类适用性和主记录定义。

**修改内容：** 建立记录清单，逐类列明批次主记录、过程采样、报警、报表、配置、审计、签名、备份及诊断日志的用途、权威原件所在位置、是否依赖电子形式、关联 predicate rule、责任人、保存期、复制/纠正/删除规则。界定 PLC、Windows、数据库、报表生成端、移动介质和工程维护端是否处于受控边界内。明确报表由谁生成；本仓库的 Report Copy 实现的是复制，不是 PDF 生成器。

**落点：** 修订项目升级说明；增加项目记录清单、系统数据流和适用性批准记录。质量负责人确认适用条款，工程人员提供实际数据流。

**验收：** 每一类受监管记录都有明确原件与保存责任，外部生成的报表也有可追溯的责任接口。不能用“在局域网”代替封闭系统定义。

### C02｜P0：关闭默认全网监听及本机旁路

**证据：** `_Launcher/launcher_settings.py:13` 支持 global/local，`:39` 默认 global；`:73` 附近生成全 profile 的端口允许规则。`_Launcher/installer/Initialize-SD_SMA.ps1:42` 默认 Global，状态解析失败也回退到 Global。`_Launcher/launcher_config.json:26` 及四服务配置使用 `0.0.0.0`。

**修改内容：** 交付基线使用经现场确认的 loopback 或指定内部接口；配置缺失/损坏时进入受限状态。防火墙限定本地地址、来源地址和必要 profile；在启动检查中核对实际监听与规则，受监管模式不能仅显示 warning 后继续扩大暴露。限制切换 global 的权限并记录变更，安装、启动、便携包使用一致基线。

**落点：** `launcher_settings.py`、`launcher_supervisor.py:163`、`launcher_config.json`、`Configure-SD_SMA-Firewall.ps1`、`Initialize-SD_SMA.ps1` 和打包配置。支持内部 IP 时，需要同步修改当前仅接受两个 host 的校验。

**验收：** 外部接口及 IPv6 不产生未批准的访问路径；损坏网络配置不会恢复全网开放；实际 WebViewer 仍可使用。WebViewer 请求通常由承载浏览器的 Windows 发起，须以现场抓包/网络证据确定来源，不能预设它来自 mappView Server。

### C03｜P0：以 UserX 会话替代共享 token / PIN 的个人身份职责

**依据：** §11.10(d)(g)，适用签名时另涉及 §11.100(a)、§11.300。

**证据：** 四服务 middleware 均对 loopback 放行：Collector `web_config/main.py:117`、Query `app/main.py:235`、DB Admin `app/main.py:1895`、Report Copy `app/main.py:591`。`_Launcher/launcher_web.py:44` 在 PIN disabled 时直接授予管理员访问。

**修改内容：** 通过经验证的 AR 侧桥接取得用户唯一 ID、姓名、角色/权限、终端、会话 ID 和有效期；Runtime 只建立关联会话，不保存第二套密码。移除 loopback 即可信的判断，服务调用使用独立机器身份。共享远程 token 最多保留为受控机器凭据，不能充当操作员身份；PIN 不再作为生产操作授权依据。初始化和紧急维护须有受控身份、限制范围及审计。

**交换要求：** 一次性 code 必须不可预测、短期有效、绑定 UserX 会话和目标服务并原子消费；不能把用户名、角色等客户端字段直接信任为身份。避免把长期 bearer token 放 URL。如 WebViewer 限制必须用 URL 传 code，交换后立即清理 URL，禁止缓存和 referrer 泄露、脱敏访问日志，并验证多标签页和重放行为。Cookie 的 Secure、SameSite 和 CSRF 策略按实际 HTTPS/嵌入方式验证。

**失效要求：** UserX 登出、账号停用、角色变化、超时、AR 重启后旧权限不能继续有效；AR 断联不得新授予权限，高风险操作拒绝。不能简单读取 PLC 上一个全局“当前用户名”来代表所有 WebViewer 会话。

**落点与验收：** 在现有 `SD_SMA_COMMON` 增加最小会话适配，接入五个服务入口；PLC 工程实现对应会话桥。验证双终端不同用户不会串号，旧 code 重放、客户端伪造角色、本机无身份请求均失败。

### C04｜P0：按后端动作授权，覆盖 Query 的 PLC 写回

**证据：** Query `app/main.py:1453` 的插件查询会进入 `_run_plugin_writeback()`，`:1490` 游标操作会写回 PLC，`:996` 激活快照也写回。仅按“查询页/操作页”或 GET/POST 分类会遗漏副作用。

**修改内容：** 制定服务端动作权限：记录读取、记录导出、PLC 写回、配置修改、采集启停、备份、恢复、导入、删除和维护。默认拒绝未登记的接口；匿名只允许最小健康状态和必要登录资源，不默认开放受监管数据读取。把查询与写回权限分开；只读用户查询时不触发 PLC 写入。后台 OPC UA 触发路径使用明确设备/自动任务身份；如为人工发起，携带原操作人的会话关联。

**落点：** 五个 Web 后端，Query `main.py` / `plugin_opcua_monitor.py` / `opcua_writeback.py` / `table_list_writeback.py`，前端仅负责显示相同权限状态。

**验收：** 对全部路由做无身份、低权限、高权限矩阵；包含直接调用 API、页面隐藏但 API 可达、POST 只读查询、插件快照/游标写回、后台触发及任务取消。新增路由未登记权限时必须失败。

### C05｜P0：真正建立 Runtime → MpAudit 审计链

**依据：** §11.10(e)。本次在活动 Python 源码中未发现 UserX / MpAudit 认证审计接入；普通日志、任务列表和配置里的 `audit` 名称不是审计实现证据。

**修改内容：** 由 PLC 桥接受 Runtime 事件并调用适用版本的 MpAudit 接口，复用其归档、保护和检索能力。事件至少包含唯一事件 ID、关联操作 ID、用户或自动任务身份、设备/终端、动作、对象及版本、发生时间、结果；受控变更保存旧值/新值，按客户 SOP 收集修改原因。秘密字段只记录凭据 ID、版本和“已更换”等信息，不能记录密码或 bearer token。

**覆盖入口：** Launcher 网络/PIN维护/凭据/服务/导入；Collector 配置增删改、活动配置、启停；Query 配置、写回及受控导出；DB Admin 备份、复制、下载、注册外部文件、恢复、导入、删除、取消；Report Copy 配置、复制/覆盖、成功/部分失败/失败。后台重试保留原发起人，不在任务完成时读取当前登录人。

**审计策略：** 所有影响受监管记录的创建、修改、删除操作必须可追溯；导出、登录失败、权限变化等按适用安全要求和风险分析纳入。无须把每个不可人工修改的自动采样点重复写成一个人工操作事件；记录其设备、数据来源和相关异常。

**落点与验收：** 公共事件适配加各模块实际副作用处的调用；PLC 侧接收逻辑在本仓库之外。改配置后能在 MpAudit 查到正确对象、人员、前后值和最终结果；密码不出现在事件内；旧事件不能通过 UI 覆盖。

### C06｜P0：补齐审计交付确认、断链和业务结果一致性

**现状：** R3 只描述通过 OPC UA 写事件，未定义持久化确认、重试、断电或 PLC 存储已满的处理。普通 OPC UA 写成功不能证明审计已可靠留存。

**修改内容：** 定义协议和可验证的完成边界：操作 ID、事件 ID、顺序、负载摘要、接收/保存结果、重复请求处理。先可靠记录授权操作意图，再执行动作，最终记录成功/失败/取消/部分完成；操作 ID 不变，事件只追加。复用现有 SQLite outbox 的可靠交付思路做最小持久待发送记录，不能拿明文队列替代正式审计库。

**故障策略：** 审计通道不可用时阻止新的高风险人工变更；连续采集是否继续由预先验证的缓冲和容量策略决定，不能随意停设备或丢采样。跨数据库、文件系统和 PLC 的动作不宣称天然原子；启动时对未完成操作重新核对真实状态并追加恢复结果，结果不确定时进入待核查，不自动显示成功。AR 端必须避免并发事件覆盖同一组共享变量。

**验收：** 模拟 AR 断联、审计满、重复发送、ACK 丢失、Runtime 在动作前/后崩溃、PLC 重启，事件不漏记、不重复执行业务，不把失败记成成功。若所用 MpAudit 接口无法证明持久化完成，必须补充受保护的可恢复交付机制及验证证据。

### C07｜P0：重做恢复、强制导入和删除的受控执行条件

**证据：** DB Admin `main.py:641` 的 confirmation 仅绑定 action/database/table，不绑定用户、会话、数据库服务器、文件摘要或 force/truncate。`:2008` 可申请该 token；`:2171`、`:2189` 执行恢复和导入；`:1771` 可删除全表行；`:1314` 删除备份及 manifest。SQL 备份使用 `--add-drop-table`（`:1078`），恢复是潜在破坏性操作。

**修改内容：** 普通生产角色禁用这些能力；授权维护流程中强制校验目标实例/库/表、源文件 ID/哈希、完整参数、操作人、原因和当前记录状态。批准后任何目标或参数变化都须重新批准。confirmation 作为防误触令牌保留，但不能称为电子签名。需要电子签名的动作使用 C16 签署绑定。

**数据保护：** 恢复优先进入隔离库核对；确需覆盖在线库时，先保留当前状态及审计、控制采集/写入窗口、确认恢复范围，再执行并核对。原始受监管记录采用追加纠正/版本或经批准恢复，不能用 force 导入无痕替换。保留期内或处于保留锁定的文件不允许删除；到期删除也应保留审批和删除结果。异常中断不能留下“恢复成功”的状态。

**验收：** token 换人、换主机、换文件、修改 force、重放均失败；未到期删除被拒；取消/断电后可证明实际恢复范围和原记录仍可追溯。

### C08｜P0：让采集重试在目标库中幂等

**证据：** outbox `queue_store.py:86` 生成记录 ID，`data_storage.py:120` 存到 `_outbox_id`；但 `:1382` 转换入库时仅保留采集时间、补采标记与业务值。目标提交与 `:549` / `:648` 标记 outbox 完成分属两次提交。`db_manager.py:711` 的普通批量插入遇断联会重试。

**风险：** 目标库已提交、outbox 未标记完成时崩溃，重启会重放。没有目标唯一约束的组可能重复记录；按业务键判冲突的组也不能证明冲突内容就是同一条事件。该结论来自调用链，现场发生频率未测试。

**修改内容：** 把稳定源事件 ID（至少是持久 outbox ID）写入目标记录，并建立对应唯一约束；或采用与业务写入同一事务的最小去重收据表。重试前后沿用 ID，重复且内容相同视为已提交；同 ID 不同内容隔离报警。逐条处理有部分成功时，按事件确认，不能仅凭整组计数推断所有行状态。

**验收：** 在目标提交后、outbox 完成前强制结束进程再启动，同一事件在目标库只有一份；改变同 ID 内容不能被静默忽略。普通数据组、唯一键组、批次开闭和跨表写入都覆盖。

### C09｜P0：明确补采数据真实性，防止丢失和伪装历史值

**证据：** `communication/data_collector.py:729` 读取一次当前快照，`:798` 将同一 `valid_data` 写入所有欠拍 `planned_time`；已有 `is_backfill` 标记，但不是过去时刻的真实测量。`database/data_storage.py:122` 在非持久模式队列满时丢弃最旧数据；示例 `config/sample_config.json:20` 未启用持久队列。

**修改内容：** 受监管原始数据默认不把恢复时快照当成过去测量。具备 PLC 历史缓存时读取真实历史值及源时间；不具备时保留缺测区间。若业务需要补齐趋势，明确作为估算/恢复快照数据，保留算法、实际读取时间、目标节拍、源数据关联，展示和导出都能区别，禁止未批准地用于放行。

**可靠性：** 受监管配置启用并校验持久队列、可靠同步设置和容量；满盘/满队列须明确拒绝接收或使用已验证的源端缓冲、报警和应急策略。接受成功应有持久依据；不能丢弃旧记录后继续显示正常。死信处置/重放记录人员、原因、原错误及结果；清理 completed 缓冲不等于删除法定原件，须先证明目标持久化。

**验收：** 断联一段时间后，历史趋势不会把恢复值无标识地显示为真实历史采样；缺测、坏点、估算和正常采样在报表中可辨。磁盘满、达到容量、重启及死信重放均有确定结果。

### C10｜P1：拆分数据库权限，保留合法批次更新能力

**证据：** `db_manager.py:305` 建表，`:349` 自动补列，`:429` 建索引；`data_storage.py:1556` 按批次号把空 end_time 更新为结批值。因此原 R5“所有采集表仅 INSERT”不能直接执行。

**修改内容：** 初始化/迁移使用独立受控账号，正常采集使用限定表 INSERT 及必要 SELECT；Query 使用只读账号；备份账号和恢复维护账号分开。原始采样禁止 UPDATE/DELETE/DROP。批次主记录若保留当前模型，使用受限数据库过程执行合法状态转换，并在同一数据库事务保留旧/新值及待上交审计关联；运行账号不具备任意 UPDATE。不能可靠限制时，将批次开闭改成追加事件，由查询重建当前状态。

**验收：** 实际服务账号无法修改/删除原始记录，但采集、换日/分表和合法结批仍工作；重复结批、不合法时间顺序和任意列更新失败，并有可追溯结果。具体部署 GRANT 须现场采证。

**证据：** Report Copy `main.py:510` 仅比较源/目标大小；`:525` 替换目标；`:576` 仅全部失败才抛错，因此部分失败时 `start_job():485` 仍写 `done`。`:191` 操作日志是本地文本，写失败被忽略。
